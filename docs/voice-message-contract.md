# Voice-message MCP integration contract

**Status:** The initial contract selects the same prompt, truthful admission result for `voice_say` and `voice_replay` (Option A). The baseline sections derive from the independently reviewed contract, with a targeted independent review of this result-timing amendment marked READY. Option B below remains a documented, unselected future alternative for both methods. No runtime validation or code authorization is implied. This describes intended, unshipped behavior and does not claim the connector implements it. The [full contract](https://github.com/sidevoice/sidevoice-core/pull/127) is canonical. Tracking: [connector #155](https://github.com/sidevoice/sidevoice-connector/issues/155) and [core #126](https://github.com/sidevoice/sidevoice-core/issues/126).

## Connector responsibilities

The initial contract targets push delivery for Codex, Claude Code, and the operator's Cursor bridge. Pull delivery is deferred; when designed, it must preserve the same logical events and stable IDs. Host liveness and wake integration are separate questions.

For inbound room events, render one canonical JSON header followed by a blank line and only the person's exact words for a voice event. A note event is JSON only and contains no fabricated user text. Keep the general reply, retry, recovery, and causal-assent guidance centralized in MCP server instructions and tool descriptions rather than repeating generic prose in every delivered event. Preserve the event's identity, provenance, context, playback-at-turn-start evidence, hearing changes, and any correlated terminal `playback_outcomes`; unknown evidence remains unknown.

`voice_connect` supplies initial reply context for the active binding. After a room event, calls such as `voice_say` use the latest received context and event ID, including when a native harness initiated the work. The selected Option A contract gives both `voice_say` and `voice_replay` a prompt admission result: accepted means stored or admitted (`pending`/`queued`), not started, completed, or heard; invalid or unsafe requests are rejected. `text_only` applies only to `voice_say`; `voice_replay` rejects when no listener is eligible. Preserve same-ID retry behavior and bind calls, lookup, and replay to the owning conversation. A transport timeout is indeterminate, so retry with the same IDs.

The planned read and replay tools address an original by ID while its text remains available. Lookup is read-only; replay needs fresh context and current focus/listener checks. A missing original returns immediate explicit failure; accepted replay can later fail to reproduce, with a correlated terminal outcome on the next relevant normal event or recovery note. Never return success-shaped output for unavailable content or claim success merely because the attempt was queued. The contract requires no durable Core archive or restart recovery; restart invalidates stale bindings and automatic playback eligibility. Keep existing hearing evidence and recovery behavior until a replacement is validated.

On a relevant return or recovery, deliver physical facts as a correlated note to the same bound conversation. A return note does not itself authorize playback: the agent may choose an explicit replay using fresh context. A focus switch before sound must prevent playback to the old conversation. Test actual MCP calls and tool-action traces in supported harnesses, including weaker models; instructions alone cannot guarantee model behavior.

## Result timing alternative: Option B (not selected)

The selected Option A returns promptly with truthful admission for both speech tools; a later playback outcome is separate. Option B is a future alternative in which either tool waits for a factual playback result. It could return when sound actually starts (`started`, which is not completion or hearing), or wait for terminal playback (`completed`, `partial`, `cancelled`, `not_started`, or `failed`). Under either boundary, accepted/queued is not success; failures such as missing text, stale authorization, focus/listener loss, or inability to play must be explicit. A bounded timeout with unknown outcome is indeterminate, same-key retries must not create duplicate playback, and waiting must not hold Core's room lock or connector admission serial path. Option B is not selected. User words still arrive through the ordinary event with the app-captured acoustic-start evidence.
